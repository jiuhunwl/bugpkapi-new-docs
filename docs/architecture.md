# 架构概览

**简体中文** · [English](architecture_EN.md)

BugPk-Api 由三个仓库组成：Go 后端、Vue 前端与本文档仓。前后端通过 `/system-api`（管理端与用户端接口）和 `/api/{apiCode}`（开放 API 网关）通信。

## 后端分层

后端采用 DDD 分层，`internal/` 下按职责划分：

```text
cmd/bugpk-api        主服务入口：加载配置、初始化基础设施、注册路由、优雅退出
internal/app         应用装配层：路由注册、启动引导、生命周期、契约测试
internal/domain      领域层：auth / user / interface / billing / payment / risk / ticket / content ...
internal/infra       基础设施：MySQL、Redis、迁移、加密、对象存储适配
internal/pkg         通用工具：日志、错误码、分页、时间、密码策略等
migrations           数据库迁移，唯一权威来源
sql/full             由迁移生成的全量初始化 SQL
```

依赖方向固定为 `app → domain → infra/pkg`，领域层不感知 HTTP 细节，路由与参数解析集中在 app 层。

## 启动流程

```text
读取 config.yaml 与环境变量
  → 校验配置（密钥、TLS、时区确认、数据库/Redis 连通性）
  → 可选执行迁移（MIGRATION_ENABLED）
  → 引导首个管理员（INITIAL_ADMIN_PASSWORD）
  → 初始化缓存、限流器、验证码提供商
  → 注册系统路由与开放 API 路由
  → 启动 HTTP 服务，暴露 /healthz 与 /readyz
  → 收到 SIGINT/SIGTERM 后停止接新请求、等待在途请求、释放资源
```

任一关键步骤失败都会阻止启动，避免"半初始化"状态对外提供服务。

## 请求路径

### 管理端与用户端

前端同域访问 `/system-api/*`，后端完成 JWT 校验、RBAC 鉴权、参数校验与业务处理。写操作统一记录操作日志；错误返回统一错误码，便于前端做 i18n 映射。

### 开放 API 网关

```text
调用方请求 /api/{apiCode}
  → 校验 API Key 与归属
  → 校验接口状态、QPS 与套餐额度
  → 参数校验与请求体规则
  → 转发上游（连接池、超时、重试策略按接口配置）
  → 结果缓存（可选）与响应规整
  → 记录调用日志（异步汇总为分钟/小时/天维度）
  → 计费扣减与流水落库
```

网关只依赖接口配置，不在代码里硬编码上游地址；新增接口通过管理后台配置即可上线。

## 数据与计费

- **接口配置**：接口、分组、上游地址、超时、缓存、限流、计费方式都在数据库配置。
- **套餐**：全站套餐、单接口套餐、点数包三类，套餐变更通过订单驱动。
- **订单与支付**：订单状态机与支付回调幂等处理分离，回调需验签、去重并核对金额。
- **调用日志**：原始日志与汇总表分离，看板只读汇总表，避免大表聚合拖垮首页。
- **审计**：管理端写操作、登录、密钥变更等进入操作日志，可按用户与时间检索。

## 部署拓扑

推荐同域部署，减少跨域与 Cookie 问题：

```text
浏览器
  │  HTTPS
  ▼
Nginx ── /system-api、/api ──> Go 服务 (127.0.0.1:8080)
  └──── 其他路径 ────────────> 前端静态产物（SPA 回退 index.html）

Go 服务 ──> MySQL 8
        └─> Redis 6+
```

后端也可以直接托管前端产物（`FRONTEND_SERVE_ENABLED`），适合单机小规模部署；规模变大后再拆成独立静态站点与独立后端。

## 扩展点

- **支付渠道**：新增渠道只需实现统一的下单、回调验签与对账接口，管理端配置密钥后即可启用。
- **验证码**：支持多种提供商，按场景配置，失败可回退。
- **内容与品牌**：站点名称、Logo、SEO、页脚、协议模板都可在后台配置，代码不绑定具体品牌。
- **国际化**：前端文案全部走语言包，新增语言只需补一份 key 结构对称的语言文件。
